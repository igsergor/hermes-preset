# Hermes в изолированном контейнере рядом с другим Hermes

Сценарий: на одном Linux-хосте уже работает один Hermes, и нужно поднять второй —
так, чтобы он не видел ни файлы хоста, ни локальную сеть, имел доступ в интернет
и одну папку на сетевой шаре.

Проверено на Ubuntu 24.04, Docker 29.x, образ `ghcr.io/igsergor/hermes-preset:latest`.

## Что даёт изоляцию

| Уровень | Как | Результат |
|---|---|---|
| Файлы хоста | ничего не монтировать, кроме тома данных | `/home`, `/etc`, `/var` хоста недоступны |
| Docker-сокет | не монтировать `/var/run/docker.sock` | нет управления хостовым Docker |
| Права | `cap_drop: ALL` + минимум обратно, `no-new-privileges` | нет `SYS_ADMIN`, `NET_ADMIN`, `DAC_READ_SEARCH`, `MKNOD` |
| Ресурсы | `cpus`, `mem_limit`, `pids_limit` | второй экземпляр не съест хост |
| Локальная сеть | правила iptables + таймер самовосстановления | LAN и docker-сети недоступны, интернет работает |
| Шара | **bind-mount одной подпапки** | видна только она, соседние каталоги — нет |
| Интернет через VLESS | MikroTik заворачивает весь .130 | контейнер выходит через тот же шлюз, что и первый Hermes |

`cap_drop: ALL` в чистом виде **ломает** образ — s6-overlay внутри требует
`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID`, `KILL`.
Без них: `s6-applyuidgid: fatal: unable to set supplementary group list`, затем
`mkdir /opt/data: Permission denied`. `MKNOD` не нужен — проверено, контейнер стартует без него.

## Запуск

```bash
export SHARE_DIR=/mnt/myfiles/igser/hermes-share   # папка на шаре, уже смонтированной на хосте
docker compose -f docker-compose.yml up -d
sudo ./firewall.sh apply
```

Проверка изнутри (снаружи видно не то, что видит контейнер):

```bash
docker exec hermes-iso /opt/hermes/.venv/bin/python3 - <<'EOF'
import socket
for h,p in [("192.168.1.1",80),("192.168.1.130",9119),("172.28.0.1",9119),("1.1.1.1",443)]:
    s=socket.socket(); s.settimeout(3)
    try: s.connect((h,p)); print(h,p,"OPEN")
    except Exception as e: print(h,p,type(e).__name__)
    finally: s.close()
EOF
```

Ожидаемо: LAN, порт хоста и docker-шлюз — таймаут; `1.1.1.1:443` — OPEN.

## Правила iptables: зачем два набора

- `DOCKER-USER` (цепочка FORWARD) — трафик контейнера **наружу** в LAN.
- `INPUT` — трафик контейнера **на сам хост**: адреса `172.28.0.1`/`172.17.0.1`
  и LAN-адрес хоста (`192.168.1.130`) принадлежат хосту, поэтому в FORWARD они не попадают.
  Без этого правила контейнер достаёт дашборд соседнего Hermes (`192.168.1.130:9119`)
  и SSH на `:22`. В цепочке `HERMES-ISO` пропускаются только `ESTABLISHED,RELATED`
  (ответы на его же соединения), всё прочее — DROP.

Правила привязаны к **подсети** `172.28.0.0/24` (фиксирована в compose), а не к IP контейнера:
пересоздание контейнера их не ломает.

IPv6 не покрыт: у контейнера его нет (Docker bridge без IPv6). Если включишь IPv6 в Docker —
нужны те же правила в `ip6tables`.

## Чтобы доступ не открывался сам

Правила iptables живут до перезагрузки. Контейнер с `restart: unless-stopped` поднимется сам,
а правила — нет, и LAN снова откроется. Это самый вероятный сценарий утечки, а не смена маршрута.

Ставится двумя юнитами:

```bash
sudo install -m 755 firewall.sh /usr/local/sbin/hermes-iso-firewall
sudo install -m 644 hermes-iso-firewall.service hermes-iso-firewall-check.service \
     hermes-iso-firewall-check.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now hermes-iso-firewall        # правила при загрузке
sudo systemctl enable --now hermes-iso-firewall-check.timer   # проверка каждые 5 минут
```

- `hermes-iso-firewall.service` — ставит правила после `docker.service`, снимает при остановке.
- `hermes-iso-firewall-check.timer` — раз в 5 минут проверяет, что правила на месте, и
  **докладывает их, если чего-то не хватает** (`firewall.sh check`). Если всё цело — молчит.

Ручная проверка состояния: `sudo firewall.sh status` → `защищён` или `НЕ ЗАЩИЩЁН`.

## Что может сделать сам агент изнутри — проверено

Контейнер работает под uid 0, но это root только внутри своих namespace. Фактические пробы:

| Попытка | Результат |
|---|---|
| `mount -t tmpfs` | `permission denied` — нет `CAP_SYS_ADMIN` |
| запись в `/proc/sys/kernel/panic` | `Read-only file system` |
| `mknod` блочного устройства | `Operation not permitted` — capability убрана |
| чтение `/dev/sda` (когда node был создан с `MKNOD`) | `Operation not permitted` — device cgroup |
| `/var/run/docker.sock` | файла нет — сокет не смонтирован |
| `/home` хоста | пусто |
| `unshare -m` | `Operation not permitted` — seccomp |
| процессы в `/proc` | только свои (PID namespace) |
| сеть в LAN / порты хоста | таймаут (правила выше) |

Выйти на хост изнутри нечем: нет `SYS_ADMIN`, нет сокета Docker, нет устройств, нет
хост-ФС, а сеть обрезана. Остаётся один теоретический вектор — **уязвимость ядра**
(общая для всех контейнеров, лечится обновлением ядра, а не настройками).

Что агент **может** сделать по своей природе, и это не про изоляцию:

- **отправить наружу то, что у него есть** — у него есть интернет. Ключ провайдера,
  содержимое `/share`, история переписки. Не кладите в шару секреты и не давайте ключ
  с широкими правами; при утечке ключ отзывается, данные — нет.
- **прочитать всё, что лежит в его томе** `/opt/data` и в примонтированной папке шары.
- **занимать выделенные ресурсы** (2 ядра / 3 ГБ) — но не больше.

## Если убрать VLESS с хоста — LAN всё равно закрыт

NAT не открывает локалку: он только подменяет адрес источника при выходе наружу.
Доступ в LAN определяется DROP по адресу назначения в `DOCKER-USER`, и этому правилу
безразлично, куда ходит сам хост — напрямую или через VLESS.

Что реально может открыть доступ (проверять при изменениях):

- правила не применены — после перезагрузки без юнитов (см. выше);
- контейнер запущен с `--network host` или в macvlan — NAT и правила не участвуют;
- в Docker включён IPv6 — правила `ip6tables` не поставлены;
- второй контейнер поднят в **другой** docker-сети — под `172.28.0.0/24` он не попадает.

## Интернет через VLESS — уже работает, настраивать нечего

Хост .130 целиком завёрнут в VLESS-шлюз на уровне MikroTik (policy routing по адресу клиента),
поэтому контейнер через обычный NAT хоста получает тот же выход, что и первый Hermes.
Проверено: `curl 'http://ip-api.com/line/?fields=country,isp,query'` внутри контейнера даёт
тот же egress, что на хосте (Sweden, OC NETWORKS).

Отдельный WireGuard-клиент на хосте не нужен: доступ к домашней WG-сети контейнеру не даётся —
наоборот, он её не видит (`10.0.0.0/8` в DROP). Заворот трафика делает роутер,
контейнер об этом ничего не знает.
